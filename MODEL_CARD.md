# Model Card: OR Workflow Phase Segmentation (Prototype)

This is a model card for the prototype checkpoint this repository trains
(`outputs/checkpoint.pt`, via `make train`) - not a description of a model
Proximie could deploy today. See
[report/technical_architecture_report.md](report/technical_architecture_report.md)
for the production system design; this document covers only what the
prototype in this repo actually is.

## Intended use

**Intended**: a structural demonstration of a causal, multi-camera
temporal-action-segmentation pipeline for OR workflow phases - proving out
the architecture (dual-dilated multi-stage TCN, attention-pooled
multi-view fusion, postprocessing, dual metric stack) end-to-end on
synthetic data that reproduces the *shape* of the real problem (long
static phases, occlusion-heavy phases, imprecise real-world camera sync).

**Not intended**:
- Clinical decision-making of any kind, in any deployment.
- Any inference on real patient data or real OR video - this model has
  never seen a real frame; see [Training data](#training-data) below.
- A benchmark of achievable accuracy on the real task - the ~99% frame
  accuracy figures below are on synthetic data specifically constructed to
  be learnable by a 145K-parameter model in CPU-seconds, and say nothing
  about real-world difficulty (see report Sec 1.1 and 4.1 for what would
  actually be required: real annotated video, active learning, domain
  adaptation across hospitals/camera hardware).

## Model architecture

- Causal, dual-dilated, multi-stage temporal convolutional network - a
  scaled-down implementation of MS-TCN/MS-TCN++ (Farha & Gall, CVPR 2019;
  Li et al., TPAMI 2020), operating on pre-extracted per-camera feature
  vectors rather than raw pixels (`src/model.py`).
- Multi-view fusion: shared per-camera projection + attention-weighted
  pooling across available cameras, trained with view-dropout (randomly
  zeroing 1-2 of the 1-3 camera streams per sequence) for occlusion
  robustness (`CameraFusion` in `src/model.py`).
- **144,975 parameters.**
- **Computed (not estimated) receptive field: 321 frames** (53.5 minutes
  at `seconds_per_frame=10.0`) - see `model.compute_receptive_field_frames`
  and `tests/test_model.py`'s exhaustive-perturbation cross-check.
- Causality is verified, not assumed: `tests/test_model.py` perturbs only
  the tail of an input sequence and asserts every earlier-timestep output
  is bit-identical - a property required for real-time/online deployment
  (Sec 4.3.1) that a shape-only test would not catch a violation of.

## Training data

**100% synthetic, generated by `src/data.py`/`src/sync.py`.** No real OR
video, real patient data, or real camera footage was used anywhere in
this repository. Specifically:

- Per-case phase durations are sampled from a Gamma distribution per
  class, rescaled to a fixed `seq_len=240` frames - `patient_present` and
  `operation` are parameterized as the two long phases, matching the
  assignment's framing of these as the two named failure modes.
- Per-frame features are a fixed per-class prototype vector (128-dim) plus
  per-camera and cross-camera Gaussian noise - real, learnable structure,
  not a trivial lookup table, but not derived from any real sensor.
- Each of 1-3 cameras' clean signal is passed through `src/sync.py`'s
  independent timestamp-jitter and frame-drop simulation, then realigned
  onto the nominal capture grid - producing a genuinely per-timestep
  camera-availability mask, mirroring the real ingestion problem's
  imperfect sync (report Sec 4.3.1) without using any real capture
  hardware or footage.
- Config: `config/default.yaml` → `data:` block. **32 training
  sequences, 8 validation sequences**, seed `42`
  (`src.config.set_seed`) - deliberately small, since the point is
  architectural validation in CPU-seconds, not a realistic dataset size.

Real training data requirements for an actual deployment (annotated OR
video, active learning over a retention-limited hard-example store,
self-supervised pretraining to cut annotation cost) are covered in report
Sec 4.1 - none of that infrastructure or data exists in this repo.

## Performance characteristics

From the most recent `make train && make evaluate` run against
`config/default.yaml` (exact reproduction steps in
[README.md#reproducibility](README.md#reproducibility)):

| Metric | Raw | Postprocessed |
|---|---|---|
| Frame accuracy | 0.994 | 0.990 |
| Edit score | 100.0 | 97.5 |
| Segmental F1@10 | 1.000 | 0.986 |
| Segmental F1@25 | 1.000 | 0.986 |
| Segmental F1@50 | 1.000 | 0.986 |
| Boundary latency (frames) | 0.1 | 0.1 |
| Cost-weighted FP/FN total | 0.0 | 1.0 |

Training: ~150-155s on a 4-core CPU, 20 epochs, no GPU. Exact numbers vary
run-to-run within a small band because the synthetic dataset's camera
counts and phase durations are themselves randomly sampled (seeded, but
error-analysis's corruption injection draws additional fresh randomness on
top - see README's "Design choices worth flagging" for detail).

**These numbers are near-ceiling by construction**, not evidence of a
strong model - the synthetic task is deliberately learnable. The
meaningful signal is the *relative* degradation under injected noise,
below.

## Known limitations (measured, not hypothesized)

`src/error_analysis.py` injects occlusion noise during `operation` frames
and background-jitter noise during `patient_present` frames - the two
phases the assignment names as the hardest - and measures the delta
against clean-input performance:

- **Raw per-class frame-accuracy drop: ~-0.53 on `patient_present` and
  `operation` vs. ~-0.01 on the other three classes.** The model is
  measurably more fragile on exactly the two named failure modes, not
  uniformly fragile - this is the intended, reproduced behavior, not a bug.
- **Postprocessing recovers `operation`'s segmental F1 but not
  `patient_present`'s frame-level error** (see report Sec 1.5's "Key
  finding" for the full breakdown) - majority-filtering and min-duration
  merging can clean up short spurious segments, but cannot fix a model
  that is systematically, confidently wrong across a sustained window.
  This is the specific reason report Sec 4.4 (Production Monitoring)
  argues that "the model is running" and "the model's output is trustworthy"
  are different questions requiring different signals.
- **No robustness claim beyond what's tested.** `tests/test_robustness.py`
  verifies the model stays numerically finite (no NaN/crash) under
  near-total camera-sync loss, sequences shorter than the receptive field,
  and single-camera high-dropout cases - it does NOT claim the
  *predictions* stay accurate under those conditions, only that the model
  degrades gracefully rather than failing catastrophically.
- **No fairness/bias evaluation** - the training data has no demographic,
  hospital-site, or camera-hardware variation to evaluate fairness across
  (it's synthetic and homogeneous by construction). Report Sec 4.4's
  per-hospital/per-camera breakdown monitoring is the design answer to
  this for a real deployment; nothing here has been measured for it.

## Ethical and clinical considerations

This prototype makes no clinical claims and should not inform any
real judgment about a model's suitability for OR use. Report Sec 4.5
(Security & Privacy) covers the actual considerations that would apply to
real patient/OR video: data minimization, retention limits, encryption,
and access control - none of which are exercised here because no real
data exists in this repository to protect.

## Provenance

Trained via `make train` (`src/train.py`) against `config/default.yaml`,
seed `42`. Checkpoint stores only tensors and plain metadata (`model_state`,
`model_config`, `feature_dim`, `num_classes`) - never a pickled config
object - so it loads with `torch.load(weights_only=True)`
(`src/evaluate.py::load_model`), the same security posture applied to any
checkpoint regardless of source.
